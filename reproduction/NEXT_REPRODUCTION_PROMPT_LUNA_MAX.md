## 四、阶段 A：复核完整评分链与配对统计

实现可恢复、可重复执行的离线审计脚本，写入新目录，不改写原结果。

1. 检查 manifest、GT、Tool/Global 预测和评分各自的 qid 唯一性、652 条覆盖、来源视频映射、无错位 join。
2. 对每条实际 judge 请求验证问题、参考答案、模型答案的来源及顺序。检查缓存 key 是否包括所有影响评分的输入和冻结配置，是否存在跨答案误命中、条件名称泄漏或参考答案进入模型输入。
3. 从原始 judge 响应重建 0/0.5/1 分数，与逐题结果逐项比较；复核 finish_reason、token、错误状态和本地无答案计零逻辑。不得将网络或解析错误转换成零。
4. 用明确公式独立重算完整集、共同有效集均值及 Tool−Global。复核 video-cluster bootstrap：同一抽样同时用于两组；重复抽中的视频必须重复计权；保持 query-weighted 均值；seed=42，10,000 次。不能先按视频求均值再无说明替代原指标。
5. 输出 3×3 配对评分列联表、Tool 胜/平/负数量、差值分布以及各单元对总差值的贡献。检查负差是否主要来自无答案、部分正确与全对互换，或大量普通已完成样本。
6. 核实相同答案是否一致命中缓存，报告缓存收益及任何不一致。不额外重问 judge 来挑选有利评分。

每个结论给出文件、qid、字段或代码位置。所有解释性分组均说明是看过结果后的探索分析，不冒充预注册验证。

## 五、阶段 B：工具链和协议差异诊断

先检查所有 652 对已有轨迹，再选择少量样本详细审阅。

全量统计至少包括：工具请求/成功次数、全局/局部帧实际数量、局部帧进入后续消息、时间戳与裁剪单位、上下文历史保留、prompt/输出 token、finish_reason、答案提取、裁剪区间宽度和相对视频位置。

重点排查：

- 全局和局部帧的顺序、时间坐标、缩放、图像与 grid/消息对应关系；原始全局帧是否在后续请求中仍然存在。
- assistant 文本和工具调用是否重复、遗漏或错序；tool_call_id 与工具结果是否正确关联；crop 输出是否包含官方预期的时间和视觉内容。
- Tool 与 Global 的 system/user prompt、禁用工具方式、chat template、EOS/stop、解码参数与答案提取是否存在会影响解释的差异。Global 是本地消融，不能默认唯一变化是“多看局部帧”。
- 无效区间、短区间采帧、解码失败的实际路径；不要从少量失败直接解释全部 8.74 分差距。
- 已知官方 async runner 历史观察丢失修正是否在本批样本中被触发；若没有多次 crop，不能宣称它解释了当前差距。
- 65,536 context 相比模型 128k 的限制是否在实际请求中触发；不要仅凭配置不同归因。stop 也不能单独证明没有 EOS/stop 问题。

样本审阅在运行前固定选取规则和 seed=42：按 Tool胜、平、Global胜分层，各最多八条，优先来源视频多样性；另外列出全部技术失败。保存 qid 清单和抽样理由，不只挑最醒目的失败。

为样本建立证据表，区分：已证实的程序错误、答案内容差异、judge 可疑判定、无法判断。允许自动审阅答案与轨迹，但不得把其意见当成独立人工真值，也不得以自动审阅结果改写冻结评分。

可分析分数差与视频时长、裁剪比例、token 成本等变量的关联；不得把事后相关性宣称为裁剪造成错误的因果证据。

## 六、阶段 C：只针对明确实现错误修复和受限复测

若没有明确实现错误：交付诊断即可，不为提高分数更换 prompt、增帧、改变工具策略或启动训练。

若发现明确错误：

1. 保存复现证据、最小 failing case、原实现与官方证据对应关系。
2. 在隔离代码/新版本文件中实现最小修正，保存 diff；不覆盖原冻结运行代码和配置。解释修正改变的是兼容性、错误行为还是方法协议。
3. 添加针对该错误的有效回归测试，先跑相关 CPU 测试。多模态问题需验证实际消息/帧或真实视频路径，不能只用与实现同构的测试替代。
4. 若必须真实模型验证，预先冻结复测清单：原固定 25 条作为基础，明确错误未覆盖时再加入必要样本，总数最多 32。保存受影响组、对照组和新配置哈希。使用授权空闲 GPU 6/7 或经核验的现有服务；资源不满足就交付阻塞说明。
5. 复测输出放新目录，记录全部尝试；将其称为工程修正诊断，不与旧结果拼接成“更高的完整集成绩”。最多两轮有明确错误证据的修正验证，不能无上限试参。
6. 默认不开展第二次全量推理。若修正影响完整成绩，提交具体全量 A/B 复跑方案、必要性、耗时和评分费用估计，作为下一次执行任务；保留原结果。
